# Проект `realty` — продукт: диалог, брони, объявления, напоминания

**Что это.** Продуктовый контур целиком: мост (`realty_agent.bridge_main`, порт `8085`), граф напоминаний
о визите (`realty_agent.reminders_main`, `8089`), MCP-листенер с инструментами для агента
(`realty_agent.mcp_main`, `8087`), разбор диалога и фильтров, брони, генерация объявлений, зрение,
очередь исходящих и две свои базы.

**Свой репозиторий, свой композ, свой образ, свой пакет `realty_agent`.** Общий код живёт в `agent_core`
и ставится колёсом (`wheels/agent_core-<версия>.whl`).

## Как запускать

```bash
cp .env.example .env     # заполнить значения: секреты в git не попадают
make up                  # поднять службы и дождаться готовности
make status              # состояние служб и подключение Telegram
make stop                # остановить (тома и данные не трогаются)
make check               # офлайн: композ разбирается настоящим парсером
make test                # офлайн-тесты (живые пропускаются, если нет адреса тестовой базы)
```

| Служба | Адрес | Что это |
|---|---|---|
| `realty-db` | `127.0.0.1:55435` | своя база продукта (`postgres:17`, том `realty-db-data`) |
| `bridge` | `127.0.0.1:8085` → `8081` | мост: разбор хода, брони, объявления |
| `reminders` | `127.0.0.1:8089` | граф напоминаний о визите |
| `mcp` | `8087` | MCP-листенер с инструментами для агента |
| `pgvector` | `127.0.0.1:55433` | векторная база RAG |
| `reminders-db` | `127.0.0.1:55434` | база чекпойнтов графа |
| `migrate` | — | накат схемы: `core,runtime,realty,vectors`, одноразово |

## Контракт с остальными

* **Сеть — общая с платформой** (`external: true`, имя в `PLATFORM_NETWORK`): создаёт её стек платформы,
  проект её не создаёт.
* **Имя проекта compose — `realty`, и оно СОХРАНЕНО намеренно.** По нему названы тома: корпус RAG
  (`corpus-data`) и чекпойнты графа (`checkpoints-data`). 
* **Имена служб и порты — контракт проекта**: по ним к службам приходят по имени в сети, поэтому меняются
  осознанно и вместе с окружением, а не «заодно».
* **Данные берутся по именам служб**: своя база продукта — служба `realty-db` ЭТОГО композа (адрес — в
  `DB_URL`), векторы — `pgvector:5432/vectors`, эмбеддинги и решатель — адреса из `.env`.
* **Каталог сессий — свой** (`SESSIONS_DIR`, том `/srv/realty/.sessions`), задаётся **настройкой**, а не
  выводится из расположения кода: в установленном пакете такой путь указывал бы внутрь `site-packages`,
  и бот молча не подключался бы.

## Окружение

Значения читаются из `.env` рядом с композом (образец — `.env.example`) — этот файл обязателен.
Общий `.env` воркспейса, если проект стоит внутри воркспейса, лончер подключает ПЕРВЫМ, для подстановки
`${…}`; в контейнер идёт только `./.env` проекта, поэтому всё, что нужно службе, должно быть в нём.

Ключи, без которых продукт не работает: `DB_URL`, `VECTOR_DB_PASSWORD`, `GRAPH_DB_PASSWORD`,
`LLAMA_EMBED_URL`, `LLAMA_EMBED_MODEL`, `SOLVER_URL`, `PLATFORM_NETWORK`, `REMINDERS_CHECKPOINT_DSN`
(для графа). Остальные — поведение, лимиты и адресаты; полный перечень с пояснениями — в `.env.example`.

## Решения

| Решение | Что этим исключено |
|---|---|
| Публикация хода и броней — в PostgreSQL, состояние хода в базе, а не в памяти процесса. | Потеря хода при рестарте и дубли после перезапуска. |
| Чекпойнты напоминаний — своя база, отдельная от корпуса RAG. | Переиндексация корпуса рискует состоянием живых потоков. |
| Векторная база — свой контейнер `pgvector`. | Зависимость от расширения в чужом образе платформы. |
| Один образ на продукт (`realty-agent:latest`) для всех служб и наката схемы. | Четыре образа из одного содержимого и накат схемы старым кодом. |
| Наблюдение — по именам служб в общей сети, хостовый откат — лончерами `bridge-up*.sh`. | Привязка процесса к сети хоста и «невидимость» напоминаний из контейнера. |
| Адреса моделей и баз объявляет `.env` продукта, в коде литералов нет. | Запрос «не туда» при переносе службы и тихий пропуск настройки. |
